# Recording the README demos

The screencasts the README and the user guide show are generated by
[`scripts/record_demos.mjs`](../../scripts/record_demos.mjs). It drives the real
Tauri app through three flows, records the app window with macOS
`screencapture`, and encodes muted MP4 + WebM into this folder, plus the looping
GIF a doc shows.

A doc cannot play a recording with a `<video>` tag: GitHub's markdown sanitiser
strips the `src` and `poster` from a `<video>` whose source is a file in the
repository (only uploaded attachments play inline), so the page would show
nothing. So the README (the getting-started take) and the user guide (the other
two) show each recording as its GIF, which plays by itself and loops, with text
links to the MP4 and WebM under it. The GIF is 960 px at 10 fps, about 3 MB for
the 72-second getting-started take; the MP4 and WebM keep 1200 px at 30 fps.
Every flow is marked `gif: true` in the script; one without it gets a poster
frame instead.

```sh
npm run record:demos                            # all three flows
npm run record:demos -- --flow getting-started  # one flow
npm run record:demos -- --flow import-csv
npm run record:demos -- --flow manual-txn
```

Flows:

- `getting-started` — the getting-started video: **one continuous take** of the
  three main features in the order a new user meets them, in a single app
  session and one throwaway vault. Choose a data folder in the vault picker,
  set the vault's base currency and add an account; import a CSV into that
  account (the app offers the file dialog as soon as the account exists) and
  map its columns in the Rhai transform; add a transaction by hand and see it
  in the list. It ends on the ledger text file the pipeline wrote for that
  account under the vault's `generated/` folder, open in TextEdit, with the
  imported rows and the manual transaction visible as ledger lines: the one
  hard cut in the take. The app has no text viewer and a window-id capture
  cannot show another app's window, so that closing shot is a second segment,
  recorded by TextEdit's own window id (sized like the app window, the file
  name in its title) and joined to the first with ffmpeg. TextEdit is driven
  through System Events and `open -a`, needs no extra permission, and is quit
  afterwards when it was not already running; its plain-text font size is
  raised to 16 pt for the shot through its preference and put back after.
- `import-csv` — the CSV import on its own, into a pre-seeded account.
- `manual-txn` — the manual transaction on its own.

Useful flags: `--keep-mov` (keep the raw capture), `--no-record` (drive only, no
video), `--no-encode` (keep the raw `.mov`), `--pace <ms>`, `--width <px>`.

## Every release: re-record the getting-started video

`getting-started.mp4`, `getting-started.webm` and `getting-started.gif` are
re-recorded from the release commit for every release and never edited by
hand, so they always show the current UI and whatever the milestone shipped. It
is a step of "Creating a new production release" in
[DEPLOYMENT.md](../../DEPLOYMENT.md), before the tag:

```sh
scripts/run_debug_mcp.sh                        # the webdriver build of that commit
npm run record:demos -- --flow getting-started  # about two minutes; writes the three files here
```

The file names do not change, so the README's GIF and its links stay on
`docs/demos/getting-started.*`. Link the recording from the version's section of
`CHANGELOG.md` (the release notes) and commit the three files with the release.
The other two recordings are only re-made when their flow changes, or when the
app's look has moved on enough that they no longer show the current app; each
re-record rewrites its `.mp4`, `.webm` and `.gif`.

## Prerequisites

- **macOS** (the script uses `screencapture` and `osascript`).
- **App binary built with the webdriver feature** — run `./scripts/run_debug_mcp.sh`
  once. The script looks for `~/.cache/emuacc-target-mcp/debug/emuaccounts`
  (falling back to `src-tauri/target/debug/emuaccounts`).
- **`tauri-wd`** on `PATH` or in `~/.cargo/bin` (`cargo install tauri-webdriver-automation`).
- **`ffmpeg` / `ffprobe`** (`brew install ffmpeg`).
- `selenium-webdriver` (already a dev dependency).

## Required macOS permissions (TCC)

The app that *hosts* the shell running the script — Terminal, an IDE, or the
tool that runs an agent — needs two permissions in **System Settings → Privacy &
Security**. macOS attributes the grant to that hosting app, not to the shell or
to `node`:

| Permission | Why | Which flows |
|------------|-----|-------------|
| **Screen Recording** | `screencapture` records the app window | all |
| **Accessibility** | `osascript` types into the native file/folder dialogs | `getting-started`, `import-csv` |

`manual-txn` is fully in-WebView and needs only Screen Recording. The other two
drive native OS dialogs via synthetic keystrokes, which silently do nothing
without Accessibility. Grant both to the app hosting your shell, then re-run.

An ad-hoc-signed host (a locally built tool rather than a notarised app) loses
its Screen Recording grant every time it is rebuilt: its entry stays in the list
but no longer applies. Remove the entry and add it again. Check both grants from
the shell itself before a run:

```sh
# Screen Recording: prints true when this process chain is granted
printf 'import CoreGraphics\nprint(CGPreflightScreenCaptureAccess())\n' > /tmp/sc.swift && swift /tmp/sc.swift
# Accessibility: fails with "not allowed assistive access (-25211)" when missing
osascript -e 'tell application "System Events" to tell process "Finder" to return count of windows'
```

## Safety

- The script never touches your real vault: it moves
  `~/Library/Application Support/com.emusoftware.emuaccounts/config.json` aside,
  points the app at a throwaway temp vault, and restores your config afterwards
  (including on crash/Ctrl-C). Demo data is seeded into the temp vault only.
- It takes exclusive ownership of `tauri-wd` on port 4444 for the duration
  (stop any MCP/`tauri-wd` session first).
